# Mabda — خريطة العمل بعد دمج الهوية

**التاريخ:** 30 أكتوبر 2026. **النطاق:** 7 مقترحات مستقبلية؛ ليست أوامر تنفيذ تلقائية. مسارات HTML وCSS وJavaScript الأساسية (22 درسًا) نشطة بالفعل. التطبيق هو المنتج القائم نفسه باسم Mabda، وVANTA هو الفريق، لا منتج تعلّم ثانٍ أو tenant منفصل. لا حاجة الآن إلى `product_id` أو نسخ قاعدة البيانات لمجرد تغيير الاسم.

العمل الحالي يحافظ على الهوية المشتركة، ويغلق التناقضات في المحتوى والـvalidators والتقدم وAuth. وجود مسارات الأساس لا يعني وحده جاهزية إطلاق إنتاجي، ولا يفتح المقترحات التالية دون مراجعة.

## ترتيب الاعتماد والأولوية

المسارات الأساسية الثلاثة مطبقة. الأولوية التالية هي التحقق التشغيلي والأمني (1–3)، ثم يمكن النظر في تعميق CSS/JavaScript (4–5) أو التحديات والمشاريع (6). تحليلات المهارة (7) تعتمد على نتائج موثوقة من 6. إعلان ميزات مستقبلية كمخططة يستمر حتى اجتياز قبول مرحلتها.

| المرحلة | العنوان | موقعها من الإطلاق |
|---|---|---|
| 1 | إثبات جاهزية الحساب والإصدار | أساسية قبل إطلاق HTML العام |
| 2 | موثوقية Studio والمسودات والتحقق | أساسية قبل الاعتماد طويل المدى على المسودات |
| 3 | إغلاق تجربة HTML والتوجيه | أساسية لاكتمال الإصدار التعليمي الأول |
| 4 | تعميق CSS بعد الأساسيات النشطة (8 دروس) | توسعة اختيارية بعد التحقق من التجربة الحالية |
| 5 | حل المشكلات بـJavaScript بعد الأساسيات النشطة (9 دروس) | توسعة تعتمد على عقود المسارات وعزل التنفيذ |
| 6 | تحديات ومشاريع بنتائج قابلة للتحقق | توسعة تطبيقية بعد الأساس |
| 7 | استمرارية المتعلم والتحليلات والنمو المسؤول | تحسينات لاحقة؛ المساعدة الذكية اختيارية منفصلة |

## 1 — إثبات جاهزية الحساب والإصدار

**الحالة والدليل:** `AuthProvider.tsx` يدير الجلسة والاستعادة وrecovery؛ `StudentAccountPages.tsx` يضم التسجيل والدخول والاسترجاع واللوحة والملف؛ `safeReturnPath.ts` يقيد العودة. الجداول الأربع وRLS وسياسات الملكية تحققت metadata فقط عبر MCP. يوجد typecheck/build واختبارات عقود محلية الآن، لكن لا CI ولا اختبار حسابين فعليين ولا إثبات كامل لدورة البريد/الحفظ. يبقى تحذير Vite للحزم الأكبر من 500KB.

**المشكلة:** لا يكفي أن ينجح build أو أن يفتح الزائر الصفحة لادعاء عمل التسجيل والتقدم المستمر أو جاهزية النشر.

**النطاق:** مجموعة اختبار بحساب طالب مؤكد، Sign Up → بريد تأكيد → callback → Login → Dashboard/Profile → درس/Quiz → حفظ → logout/login → استعادة. اختبار password recovery والجلسة المنتهية وتبديل حسابي A/B. إضافة CI محلية التعريف للتأكد من types/tests/build/diff وعقد المسارات. توثيق origin/redirects وSPA fallback وبيئة SMTP للإطلاق المختار. تقليل تحميل shell والمحتوى لتحديد budget قابل للقياس؛ error boundary وحالات فشل الأصول. إغلاق أساسيات keyboard/focus/contrast على كل حالات الحساب، لا مجرد الصفحة الابتدائية. مراجعة اتساق طول display_name بين UI/service/SQL دون تغيير صامت.

**الاعتماديات:** موافقة المرحلة الحالية؛ حساب/جلسة اختبار مؤكدة؛ قرار بيئة الاستضافة والنطاق قبل أي تغيير redirect أو نشر. لا تتغير إعدادات Auth الآن لمجرد إعادة الهوية.

**الملفات/الأنظمة:** `tests/`, `package.json`, إعداد CI مقترح في `.github/workflows/`, `AuthProvider`, `StudentAccountPages`, `studentData`, `safeReturnPath`, `vite.config.*`, `docs/`, وإعداد الاستضافة لاحقًا. أي تعديل SQL يكون migration مستقلة مع types واختبارات.

**القبول:** دورة المصادقة الفعلية موثقة بلا بيانات اعتماد في التقرير؛ A لا يقرأ/يكتب صفوف B؛ تقدم ومسودة A يعودان بعد logout/login؛ فشل الشبكة لا يظهر كنجاح؛ direct links وcallback/reset تعمل على origin الموافق؛ gate CI يمر؛ تحذيرات performance لا تخفى برفع حد التحذير فقط.

**الاختبارات:** unit/component للـguards وcallbacks وsession changes؛ authenticated E2E على جهازين/متصفحين عند الإمكان؛ RLS integration بحسابين؛ كشف أسرار؛ direct routes؛ 320/390/768/1440 بالعربية والإنجليزية؛ keyboard وقارئ شاشة؛ bundle budget.

**المخاطر/قرارات الموافقة:** بريد الحساب والخصوصية والاحتفاظ ببيانات الاختبار؛ النطاق والاستضافة/النشر يتطلبان موافقة منفصلة؛ هل تعديل اسم مرسل البريد إلى Mabda مطلوب؟ لا يتم تلقائيًا. اختبارات خارج Chromium وأجهزة الهاتف الحقيقية لم تنفذ في المرحلة الحالية.

## 2 — موثوقية Practice Studio والمسودات والتحقق

**الحالة والدليل:** `PracticeStudio`, `PracticeCodeEditor`, `practiceDiagnostics`, `practicePreviewDocument`, `practiceValidation` وخدمة `practiceDrafts` تعمل ضمن HTML. Run/checklist/Quiz منفصلة وReset محلي؛ static diagnostics وروابط مواقعها وruntime/stale preview موجودة. كود البداية غير محلول. الحفظ يدوي، والصف الواحد قد يكتب فوقه تبويبان؛ `draft_version` ليس optimistic concurrency حقيقية. validator الحالي heuristics وليس متصفحًا كاملًا.

**المشكلة:** احتمال فقد تعديل غير محفوظ أو تعارض نسختين، وقبول متطلبات مستوفاة بعناصر مختلفة، وفشل المعاينة دون recovery كافٍ. العزل التعليمي لا يعادل بيئة تشغيل مطلقة الأمان.

**النطاق:** تعارض revisions وواجهة مقارنة/اختيار قبل الاستبدال، IDs منفصلة لعمليات load/save، إعادة مصالحة بعد تبديل الحساب، local recovery اختياري مع TTL وحماية خصوصية وموافقة UX، وتنبيه مغادرة المسودة غير المحفوظة. تقوية validators لربط `href` والنص داخل **الرابط نفسه** و`src` و`alt` داخل **الصورة نفسها**، ومعالجة quoted `>` والوثيقة الناقصة بقواعد parser واضحة. watchdog لاستعادة حالات load/message المفقودة، schema للرسائل واختبارات frames القديمة. تقييم token باستخدام crypto. دراسة عزل التنفيذ والتعامل مع حلقات JavaScript المتزامنة؛ timeout داخل الحلقة نفسها لا يضمن إيقافها.

**الاعتماديات:** المرحلة 1 واختبار حسابين؛ قرار حفظ تلقائي/يدوي ومحلي؛ migration مصرح بها قبل إدخال revision جديدة. لا توسعة RLS بلا سبب موثق.

**الملفات/الأنظمة:** مكونات Studio، `src/utils/practice*`, `src/services/practiceDrafts.ts`, `src/lib/database.types.ts`, migration draft revisions عند الموافقة، ترجمة حالات conflict/recovery والاختبارات.

**القبول:** لا استبدال صامت لمسودة أحدث؛ Reset لا يكتب للسحابة؛ فشل save يظل ظاهرًا مع retry لا نجاح زائف؛ الكود المتأخر من iframe قديم لا يلوّث الحالة؛ نموذج رابطين/صورتين لا يجتاز شرطًا يطلب عنصرًا واحدًا صحيحًا؛ Run لا يغير score/completion. حدود تشغيل الحلقات موثقة ومختبرة في بيئة قابلة للاستعادة قبل أي ادعاء بالعزل القوي.

**الاختبارات:** حسابان/تبويبان، edit-during-save وreload/auth switch/network failure، malformed/valid fixtures باللغتين، source/token spoof tests، asynchronous/runtime/stale cases، recovery من absence-of-message. اختبار خطر تعليق الحلقة داخل بيئة اختبار معزولة قابلة للإيقاف، لا داخل جلسة صاحب المشروع.

**المخاطر/الموافقة:** ترحيل revisions وسياسة الاحتفاظ وlocal recovery، إضافة autosave دون فقد manual checkpoint، وأي تغيير حدود التنفيذ/الخادم يحتاج threat model وموافقة. لا ادعاء مساواة VS Code أو حماية مطلقة.

## 3 — إغلاق HTML وتوجيه المتعلم

**الحالة والدليل:** `HTML_LESSON_IDS` يثبت خمسة دروس، أربعة اختيارات وإجابة واحدة لكل سؤال، ثبات الخلط عند retry ودرجة أول محاولة. مسار HTML وحده available. Intro يستعمل `initialHtmlExercise.ts`، والإكمال يشتق من نتيجة Quiz؛ ليس من Run. يوجد resume/recommendation في `learningProgress` لكنه يحتاج إثباتًا فعليًا بالحساب.

**المشكلة:** وجود خمسة دروس لا يثبت تمكن الطالب من تركيب صفحة أو فهم أخطائه. هناك خصوصية في مكوّن الدرس الأول وrubric/نتيجة تحتاج قرارًا تربويًا واضحًا.

**النطاق:** مراجعة أهداف الدروس الخمسة وربط الشرح بالتمرين والـfeedback، تمرين HTML تركيبي صغير متدرج دون بناء نظام Projects كامل، hints تدريجية لا تكتب الحل تلقائيًا، محتوى عربي طبيعي متكافئ مع الإنجليزي. تثبيت تعريف completed، وهل practice شرط اختياري أم إلزامي؛ القرار لا يربط Run تلقائيًا بالإكمال. تبسيط onboarding/next/resume وإزالة نسخ منطق مكررة فقط إذا أمكن حفظ سلوك الدرس الأول. لا حذف `initialHtmlExercise`.

**الاعتماديات:** 1 و2؛ قرار عتبة النجاح وطريقة احتساب التحسن والمحاولات. لا دمج التمرين والـQuiz دون موافقة تعليمية.

**الملفات/الأنظمة:** `src/content/`, `src/i18n/learningSystem.ts`, `messages.ts`, `practiceStudio.ts`, `StartLesson`, `LearningLesson`, `LearningSystemPage`, `learningProgress` واختبارات المحتوى.

**القبول:** كل هدف له ممارسة أو سؤال يقيسه؛ الطالب يستطيع بناء وقراءة صفحة HTML أساسية؛ wrong feedback يشرح الخطأ ويتيح retry؛ outcome/next/resume متسقة للزائر والحساب؛ لا حلول مسبقة في starter؛ لا ادعاء تغطية كل HTML أو تقدم دائم للزائر.

**الاختبارات:** content parity، كل سؤال/خيار وshuffle/score/retry، تمرين تركيبي إيجابي/سلبي، navigation من أول الدرس إلى نهاية المسار، 320px وkeyboard وRTL/code-LTR، persistence مع حساب بعد إقرار تعريف completion.

**المخاطر/الموافقة:** كمية المحتوى، gating الدرس، مستوى اللغة التعليمية، وعدم تحويل تجربة عملية قصيرة إلى كورس نصي مزدحم. تعديلات قواعد النجاح أو المحتوى الكبير للمراجعة أولًا.

## 4 — مسار CSS عملي منظم

**الحالة والدليل:** `css-fundamentals` نشط ويضم 8 دروس مع محتوى ثنائي اللغة، AST validation، تقدم ومسودات مرتبطة بمعرّفات CSS. هذه المقترحات تتعلق بالتوسعة التالية، لا بتفعيل المسار.

**المشكلة:** الأساسيات الحالية لا تغطي بعد كل حالات CSS المتقدمة؛ كما أن زيادة مرونة المطابقة قد تخلق قبولًا خاطئًا إن لم تُختبر بعناية.

**النطاق:** بعد مراجعة الدروس الحالية، يمكن اقتراح موضوعات متقدمة في cascade وlayout/responsive مع Rubrics قابلة للفحص. الاستفادة من Studio والـvalidator الحاليين؛ لا إنشاء محرر ثانٍ ولا تغيير schema/RLS إلا إذا ظهرت حاجة مثبتة وموافَق عليها.

**الاعتماديات:** مراجعة تجربة CSS النشطة أولًا؛ أي إضافة جديدة تحتاج اعتماد المحتوى ومعاييرها واختبارات توافق المتصفحات.

**الملفات/الأنظمة:** `content`, `i18n`, `PracticeStudio`, CSS validators واختبارات browser؛ لا تعديلات قاعدة بيانات مفترضة.

**القبول:** أي درس إضافي له هدف وstarter/validator/feedback/quiz بالعربية والإنجليزية؛ تقبل القواعد فقط الحلول المقصودة؛ التقدم والمسودات المستمران يظلان صحيحين، ولا يتراجع HTML أو CSS الحالي.

**الاختبارات:** computed-style/cascade cases داخل iframe عند الحاجة، valid/invalid CSS، regression للمسارات الحالية، parity المحتوى، mobile responsive وreduced motion.

**المخاطر/الموافقة:** عدد الدروس، اختلاف دعم CSS بين المتصفحات، مرونة الحلول الصحيحة، وأي توسعة schema؛ لا نعاقب اختلافًا بصريًا مقبولًا بمقارنة صورة صارمة.

## 5 — JavaScript وأساسيات التفكير وحل المشكلات

**الحالة والدليل:** `javascript-fundamentals` نشط ويضم 9 دروس مع تشخيص syntax/runtime وAST validation للمطلوب التعليمي. لا يوجد بعد verifier خادمي أو نموذج موثوق لمحاولات مسائل موسعة.

**المشكلة:** الدروس الأساسية لا تثبت وحدها مهارة حل مسائل مفتوحة أو صحة تشغيلية موثوقة؛ ومخرجات العميل ليست دليلًا خادميًا على الكفاءة.

**النطاق:** إن تقررت توسعة المنهج، أضف مسائل صغيرة مفتوحة مع I/O وتلميحات متدرجة واختبارات معلنة. حدّد worker/sandbox مناسبًا لنوع الكود؛ تشغيل الوظائف النقية يختلف عن DOM. أضف step execution/console فقط إذا ثبتت ضرورتها التعليمية، مع تعريب الأخطاء وقبول الحلول البديلة الصحيحة.

**الاعتماديات:** 2 لعزل التنفيذ؛ 3 للـrubrics؛ موافقة على منهج التوسعة وحدود زمن/ذاكرة قبل runner أقوى.

**الملفات/الأنظمة:** محتوى وترجمة المسائل الإضافية، runner/verification abstraction عند الحاجة، Studio، واختبارات browser/worker.

**القبول:** مسائل بسيطة لها correct/incorrect cases قابلة للتفسير، وحالة فشل وتعافٍ؛ لا تعليق صامت ولا حلول تلقائية؛ الإجابات البديلة الصحيحة مقبولة؛ تقدم صحيح مستمر؛ الفصل بين Run والاختبار التعليمي باقٍ.

**الاختبارات:** boundary I/O، syntax/runtime/async/time-limit، malicious-message cases، loops في بيئة معزولة، DOM لا يلمس الصفحة الأم، parity وحسابات progress وmobile regression.

**المخاطر/الموافقة:** تعليم الأطفال/المبتدئين وحدود الصعوبة، runner وتكلفته إن صار خادميًا، توفير تلميح مقابل كشف الحل، ومنع الادعاء بأن نتائج العميل شهادة مهارة.

## 6 — تحديات ومشاريع بنتائج قابلة للتحقق

**الحالة والدليل:** Challenges/Projects رؤية في الهبوط وليست كيانًا وظيفيًا. درجات Quiz الحالية client-submitted summaries وRLS تثبت الملكية لا صحة المهارة. لا attempt history/submission/versioned rubric/جوائز موثوقة.

**المشكلة:** لا يمكن بناء مشاريع ومنافسة/شهادات على score قابل للكتابة من العميل أو إكمال بمجرد تشغيل المعاينة.

**النطاق:** نموذج requirements/rubric/version/submission/attempts وحالات مسودة/مراجعة/إنجاز، تحديات مرتبطة بمخرجات الدروس، مشاريع صغيرة بمراحل قبول. إقرار verifier خادمي أو آلية مراجعة قبل أي ranking/award. لوحة تقدم مبنية على milestones فعلية لا نقرات؛ حفظ evidence بما يناسب الخصوصية. مرحلة مسابقات عامة منفصلة لاحقًا وليست مشمولة تلقائيًا.

**الاعتماديات:** 1–5 بحسب لغة المشروع؛ موافقة schema/security/cost ومعايير الإكمال والمراجعة. لا نقل بيانات الطلاب أو إعادة ضبطها.

**الملفات/الأنظمة:** entities/content registries، صفحات submissions والمشاريع، services/types/migrations/RLS، verifier server/Edge Function إن وافقت صاحبة المنتج، reports.

**القبول:** متطلبات واضحة وحلول بديلة صحيحة، كل milestone له دليل، attempts لا تستبدل التاريخ بصمت، لا cross-user access، لا client-forged award؛ الطالب يستأنف مشروعه بعد الدخول مجددًا.

**الاختبارات:** verifier/rubric fixtures، تزوير النتيجة وإعادة الإرسال، idempotency، RLS بحسابين، المحتوى ثنائي اللغة، project recovery وتدرج المراحل وresponsive.

**المخاطر/الموافقة:** نزاهة النتائج، التكلفة والإساءة وملكية الأعمال ورفع الملفات؛ أي شهادات أو leaderboard أو منافسات تحتاج قرارًا ونموذج تهديد مستقلين.

## 7 — الاستمرارية والتحليلات والنمو المسؤول

**الحالة والدليل:** Dashboard/ملف/ملخص تقدم/استئناف موجودة؛ لا زمن تعلم موثوق ولا تحليل أخطاء/محاولات طويل المدى ولا تفضيلات تعلم أو أدوات خصوصية مكتملة. لا AI حاليًا.

**المشكلة:** إكمال دروس وعدّاد نتائج لا يكفيان لتوجيه تعلم طويل المدى أو قياس التحسن.

**النطاق:** أهداف وتوصيات قابلة للتفسير من بيانات محدودة وموافقة، مقارنة محاولات بعد نموذج 6، إعدادات الحساب وتصدير/حذف/retention وفق سياسة صريحة، مراقبة أعطال وأداء بلا كود طالب أو أسرار في logs. تحسينات a11y/موبايل مستمرة وعمليات دعم. المساعدة الذكية اختيارية كمرحلة فرعية منفصلة بعد تقييم الخصوصية والتكلفة ودقة النصائح؛ ليست شرطًا لإطلاق المنتج ولا تُعرض كميزة قائمة.

**الاعتماديات:** 1–3 لتحسين الاستمرارية الأساسية؛ 6 لأي استنتاج مهارة من attempts؛ سياسة خصوصية وموافقة قياس واضحة.

**الملفات/الأنظمة:** StudentDashboard/Profile، progress summaries، consent/settings، retention/export/delete APIs المصرح بها، analytics/event taxonomy ومراقبة، docs؛ AI connector منفصل إن اعتُمد لاحقًا.

**القبول:** كل metric له تعريف ومصدر وحدود، يمكن تعطيل القياس الاختياري، لا fabricated streak/accuracy، توصيات لا تمنع التعلم، حذف/تصدير آمنان مع تحقق الهوية؛ لا نسب نجاح أو وعود تعليمية بلا دليل.

**الاختبارات:** event minimization/consent، account ownership، retention/export/delete في بيئة اختبار فقط، metrics correctness وlocale dates/numbers، قارئ شاشة ومتصفحات/أجهزة حقيقية وperformance budgets.

**المخاطر/الموافقة:** سياسة البيانات والمحتوى والاعتماديات الخارجية والتكاليف. التنبؤات وAI والمنافسات والتوسع الاجتماعي مؤجلة ولا تنفذ تلقائيًا.

## قرارات لا تُحسم تقنيًا وحدها

1. اعتماد تفاصيل Hero/الفراغات/أحجام الأقفال والأزرار بعد تجربة الهوية الحالية.
2. حساب اختبار مؤكد واختبار البريد، دون مشاركة كلمة مرور في الدردشة.
3. تعريف completion ودور practice والتلميحات ونوعية المشاريع.
4. حفظ يدوي مقابل autosave وlocal recovery ومدة الاحتفاظ.
5. النطاق والاستضافة وredirects والنشر؛ هذه المهمة لم تنشر شيئًا.
6. نتائج تعليمية فقط أم لاحقًا جوائز وشهادات؟ الاختيار الثاني يحتاج تحققًا موثوقًا منفصلًا.
7. مصدر vector معتمد لاحقًا لتحسين دقة الأقفال؛ لا تحويل Raster إلى شعار بديل من طرفنا.

**نقطة التوقف:** تسليم المرحلة الحالية للمراجعة، ثم انتظار الموافقة قبل المرحلة 1 أو أي توسعة محتوى/DB/نشر.
